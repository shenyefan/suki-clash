# 锁屏期间请求与日志检查

检查日期：2026-11-09，Windows。前半记录整改前的日志与源码评估，文末记录用户确认后的实现及验证；未修改本机用户设置或系统网络。

## 结论

需要处理本地控制通道异常和持续轮询开销，但现有证据不支持“锁屏时停止所有请求”。内核连接日志包含其他程序的真实后台连接；停止界面查询不会停止这些连接，停止内核或清除代理则会影响后台联网。

日志没有锁屏、解锁、休眠或恢复事件，不能将错误开始时间认定为锁屏时间，也不能确认锁屏是管道异常的原因。后续复现应分别记录锁屏但保持唤醒、休眠恢复、窗口隐藏三个场景。

## 建议处理顺序与验证

1. 优先复现本地通道超时及错误 231。记录锁屏/恢复的准确时间、当前内核代次、API 路径、请求阶段和服务端活动连接数，确认是服务监听、内核 IPC、响应过慢还是资源释放问题；保持日志脱敏。只有取得证据后再修对应所有者。
2. 生命周期定时器跳过错过的 tick，避免恢复后补执行历史健康检查与调度；订阅更新仍基于持久化最后成功时间判断到期，不能因跳过 tick 而丢失到期操作。
3. 减少无新日志时每 250 ms 的服务请求。优先评估在现有服务边界提供有界等待的新日志读取，或按实际环形缓冲区容量设计空闲退避；保留游标、会话身份、日志持久化和退出取消。不能仅停止采集而继续宣称日志完整。
4. 按平台窗口可见性减少非必要的代理列表与配置轮询和界面通知，恢复可见后读取一次最新状态。必要流量历史、文件日志、内核与系统代理生命周期保持独立所有权。用户后续明确：CV 没有的锁屏专项逻辑不补，不用窗口失焦代替隐藏。
5. 保持真实错误与旧数据，避免恢复阶段重复 toast；不能关闭 TUN、自动改端口或修改用户设置来消除日志。

验收至少覆盖锁屏但保持唤醒、休眠恢复、窗口隐藏/恢复，服务与子进程模式分别检查。比较前后每分钟请求数、失败次数、进程/句柄变化、后台流量历史连续性、日志游标缺口及恢复后的状态一致性；注入延迟响应验证退出/目标变化能取消旧任务。其他程序主动重试仍会产生真实连接日志，不以日志完全消失作为成功标准。

## 用户确认后的实现

- `monitor` 保留后台 connections、traffic、memory 采集、流量账本及日志；代理读取改为可见时每 15 秒，隐藏停止周期读取。初次绑定、显式刷新及目标变更仍允许读取；恢复可见刷新一次。
- Controller 始终接收最新采样，但窗口隐藏时不因常规采样通知界面；仪表盘离开当前页面时停止会话引起的图表通知，返回时通知一次。
- 生命周期事件保持实时更新；状态 API 检查为可见时每 30 秒。服务归属每 5 秒独立检查，真实子进程退出检查仍保留。所有生命周期定时器设置 `MissedTickBehavior::Skip`。
- 状态 API 连续失败三次前保留就绪与代理，成功重置计数；持续失败后只进入一次失败状态，删除原先失败后又自动发布就绪、再次失败清理代理的路径。代理视图与统计流前两次连接失败仅记录 debug，达到既有三次阈值才向界面报告；保留已有数据，断流有效性仍单独更新。
- 参考 CV `src-tauri/src/core/service.rs` → `runstate/owner.rs`：服务状态暂时不可读容忍三次，再验证私有内核端点；内核仍可响应则保留代理并重置计数。启动／恢复中的缺失 PID 不视为退出，其他状态连续三次缺失 PID 才判定停止。确认归属变化、明确停止或 Fatal 则即时处理。服务状态及内核同时不可达时保留两项错误原因。
- 不添加 WTS／锁屏专项监听。没有把普通失焦当作不可见。

## 错误 231 的两条通道与修复边界

Windows `ERROR_PIPE_BUSY` 表示该次打开时没有空闲管道实例；微软的命名管道客户端示例要求等待空闲实例再打开。它本身不证明句柄泄漏，也不等于触及某个固定实例数量上限。

日志中的 12:19:41、12:20:00 来自后台服务控制管道，12:20:07 来自内核 `/memory` WebSocket 的私有管道，两个端点不能混为同一个问题。

读取 CV 锁定的 `kode-bridge 0.5.2` Windows 实现可见：监听器接受当前实例后创建下一实例；客户端遇到 231 每 5 ms 等待后重开。接受与新建之间存在暂时无空闲监听器的窗口，隔离测试用单个占用实例再补建监听器已复现这种情况。

Suki 服务客户端此前只打开一次，231 立即抛出。现改为仅在请求发送前遇到 231 时每 5 ms 等待，受现有整个请求超时约束；拒绝访问等其他打开错误直接返回。成功打开后继续校验注册的 SYSTEM 服务进程身份，保留协议与 owner/session 鉴权。已发送请求从不自动重放，丢失写操作响应仍由领域工作流回读确认。

同时移除普通服务调用前重复的 `/magic` 预探测：原来日志每 250 ms 读取一次时，每次先探测再读日志，名义上产生 8 次连接／秒；现在每次仅实际请求，名义上 4 次／秒。保留服务所有者就绪检查所需的独立 `ping_at`。这只是减少重复连接，日志采集周期与游标保持原样。

内核客户端已有约 3 秒打开重试，231 出现在它耗尽预算后；本批没有把它改成无限等待。服务端日志目录仍因 ACL 不可读，没有现场服务／内核句柄与监听器数据，无法确认当天持续繁忙是服务处理阻塞、内核阻塞还是句柄积压。`kode-bridge` 的 flush/linger 行为仅为后续排查线索，未据此修改依赖或宣称已定位泄漏。
