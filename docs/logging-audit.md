# 日志全局审核（2026-11-06）

范围：`src/` 全部程序日志触发点、内核输出采集、脚本执行日志、诊断导出，以及 `platform-service/` 的服务日志。第三方依赖日志不记录（`ProgramLogger` 仅接收 `suki_clash`、`suki_clash_service` 目标）。

## 1. 规范

### 1.1 级别

| 级别 | 使用条件 | 示例 |
|---|---|---|
| ERROR | 一次操作失败或功能不可用，需要人工关注；每次失败只在失败边界记录一次原因，再由操作层记录一次结论 | 启动内核进程失败、订阅更新失败、设置文件解析失败 |
| WARNING | 已降级但仍可继续，或已提交结果附带残留问题 | 测速存在失败项、内核更新已提交但恢复目录未清理、服务应答丢失后重试 |
| INFO | 运营人员需要还原时间线的生命周期事实和业务结果，且频率低（每次用户动作或定时任务至多一条） | 应用启动、内核已就绪、自动更新订阅完成、系统代理已写入、诊断已导出 |
| DEBUG | 排查问题才需要的过程信息：请求开始与结束、设置字段、批次、缓存、重试、守卫写入 | 开始处理某命令、测速批次开始、图标缓存就绪 |
| TRACE | 协议帧、逐条数据、逐字节 | 服务命令分发 |

INFO 不记录：命令开始、命令正常结束、设置保存、目录与文件操作、缓存加载、测速正常结束、逐节点结果、周期轮询。这些统一记录为 DEBUG。

### 1.2 文案

格式：`<对象><动作><结果>[，补充事实][（原因）]`。

- 一条日志一句话，句末不加标点，使用中文，数字使用阿拉伯数字。
- 补充事实用逗号和自然短语表达，例如“共 3 项”“请求编号 12”“内核代次 4”。
- 原因直接放在全角括号内，原文保持不变，不加“原因是”“原始错误”“详情”等前缀；多层原因在同一括号内用逗号分隔。
- 模块由日志来源列显示，正文不重复模块名。
- 不使用冒号、等号、分号、方括号拼接（日志行的来源列除外），不输出 `key=value`、调试结构体前缀或函数名。
- 不重复模块名（模块来自日志来源），不重复“失败”“错误”字样。
- 开始用“开始……”，成功用“……已完成”，失败用“……失败”。
- 不记录凭据、订阅地址、配置正文；公共脱敏仍在发布前执行。
- 内核标准输出按原文保存，不改写。

输出行：`<本地时间 RFC 3339> <级别> [<来源>] <文案>`，例如：

```
2026-11-06T10:21:08+08:00 INFO [core::service] 自动更新订阅完成，共 3 项
2026-11-06T10:21:09+08:00 ERROR [core::launch] 创建内核运行目录失败（Permission denied (os error 13)）
```

### 1.3 重复与归属

- 一次失败最多两条 ERROR：失败边界的“原因”记录（`diagnostic_error` 等），以及操作层的“结论”记录（含请求编号与是否已提交）。
- toast 不再写日志；界面层不重复记录已由执行端记录的失败。
- 用户输入校验失败（正则无效、字段为空）只用 toast，不写日志。

## 2. 审核结论与处理

### 2.1 已修复

| 编号 | 问题 | 位置 | 处理 |
|---|---|---|---|
| A1 | 每个命令开始与结束各写一条 INFO，设置保存还额外列出字段，日常使用时 INFO 被淹没 | `core/service.rs` | 开始、结束、设置字段改为 DEBUG；失败 ERROR 保留并补充“是否已提交” |
| A2 | 存储命令（打开目录、导出诊断等）开始与完成均为 INFO | `integration.rs` | 开始 DEBUG；完成仅导出诊断为 INFO，其余 DEBUG |
| A3 | 同一次失败被记录四次：原因、`请求失败`、桥接层转发、`界面错误` | `core/bridge.rs`、`ui/mod.rs` | 去掉 `show_error` 内的日志；桥接层对新请求失败不再转发；保留原因与结论各一条 |
| A4 | 测速一次产生三条 INFO：操作开始、批次开始、测速完成；合并请求也是 INFO | `core/service.rs`、`core/delays.rs`、`core/bridge.rs` | 删除操作开始；批次开始、合并、全部成功的完成改为 DEBUG；存在失败项为 WARNING |
| A5 | 出口 IP 刷新开始与完成均为 INFO | `core/service.rs`、`core/monitor.rs` | 开始、成功完成改为 DEBUG；失败 WARNING |
| A6 | 自动更新订阅/覆写开始与完成各一条 INFO | `core/profiles.rs`、`core/overrides.rs` | 开始 DEBUG；完成 INFO 并带数量；失败 ERROR |
| A7 | 退出清理细节、日志任务强制停止为 INFO | `core/bridge.rs`、`core/service.rs` | 改为 DEBUG |
| A8 | 启动阶段自启动同步、启动脚本失败只写入内存，没有写入文件，并与后续 WARNING 通知重复 | `core/service.rs` | 删除直接发布，由统一通知路径以 WARNING 写入文件 |
| A9 | 系统结束清理未完成只写入内存 | `core/bridge.rs` | 改为 `log::error!`，同时写入文件 |

| A11 | 平台服务启动内核时用 INFO 输出完整配置结构，并为套接字清理写四条 INFO | `platform-service/src/core/manager.rs` | INFO 只保留“启动内核进程”，配置与套接字细节改为 DEBUG |
| A12 | 遗漏：应用启动、系统代理写入、清除、回滚、守卫重写没有日志 | `main.rs`、`system_proxy/mod.rs` | 补充 INFO（启动、写入、回滚、清除）与 DEBUG（守卫重写） |
| A13 | 日志与存储命令共用容量 64 的队列，队列满时日志不写文件且不按级别过滤，并可能使设置保存返回“存储任务较多”（原 B1） | `integration/service.rs`、`logging/writer.rs` | 独立日志线程与容量 4096 的队列；超过 75% 仅接收 WARNING 及以上，满则丢弃并由日志线程写一条 WARNING 汇总丢弃数；删除 `Command::Log` |

### 2.3 触发点分布（修复后）

| 级别 | 来源 | 触发点 |
|---|---|---|
| ERROR | 命令执行 | 命令失败、提交被拒绝、退出清理失败 |
| ERROR | 内核 | 启动校验或 Mihomo 进程失败、进程检查失败、运行目录与通道权限失败、本地通道或握手失败、流解析失败 |
| ERROR | 基础设施 | HTTP 代理无效、客户端创建失败、请求失败、设置文件解析失败、panic、`diagnostic_error` 原因记录、日志文件写入失败 |
| ERROR | 定时任务 | 自动更新订阅或覆写失败、测速任务异常或批次被拒绝 |
| WARNING | 降级 | 测速存在失败项、出口 IP 检测失败、服务应答丢失后重试、内核更新残留、目录元数据同步失败、日志窗口缺口、界面通知中的警告 |
| INFO | 生命周期 | 应用启动、开始退出、内核已就绪、内核已停止 |
| INFO | 业务结果 | 自动更新订阅或覆写完成、系统代理写入、回滚、清除、诊断导出完成、界面提示中的操作结果 |
| DEBUG | 过程 | 命令开始与结束、设置字段、存储命令开始与结束、启动与停止中、测速批次、测速超时、图标缓存、出口 IP 成功、系统代理守卫写入、平台服务套接字清理 |
| TRACE | 服务协议 | 平台服务命令分发 |
